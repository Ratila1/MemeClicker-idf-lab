# Техническое задание: платформа соревновательного кликинга в реальном времени

**Версия:** 1.1 (срок: 8 часов)

**Стек:** Java 25, Spring Boot 4.0.x, Spring MVC + Virtual Threads, **Gradle (Kotlin DSL, Wrapper)**, React + Vite, Kafka, Redis.

**Деплой:** Render.com (Web Service, Docker) + внешние managed-сервисы.

---

## 1. Цель

Мини-игра для соревновательного кликинга. Игроки заходят в единое лобби по никнейму. При наборе минимум 5 человек и единогласной готовности стартует 60-секундный раунд. Каждый клик проходит через Kafka, обрабатывается консьюмером и обновляет лидерборд в Redis. Фронтенд получает лидерборд и статус лобби по WebSocket. Итоги раунда и история матчей сохраняются в Redis.

**Ключевые требования:**

- Игра стартует одновременно у всех (расхождение не более 1 с).
- 5 игроков × 10 кликов/с без деградации.
- Через 60 секунд кнопка блокируется, показывается финальный экран победителя.
- Идемпотентность кликов, backpressure, graceful shutdown без потери кликов.
- **Ни один принятый клик не теряется и не считается дважды.**

## 3. Архитектура

```
[React SPA] --REST--> [Spring MVC + Virtual Threads]
     ^                        |
     |<-----WebSocket---------+  (лидерборд, статус лобби)
     |                   +----+-----+
     |                   v          v
     |             [Redis]      [Kafka Producer]
     |             (лобби)      (клики, acks=all)
     |                              |
     |                              v
     |                  [Kafka: clicks, 1 партиция]
     |                              |
     |                              v
     |              [Kafka Consumer в том же приложении]
     |                              |
     |                  Lua: SET NX dedup + ZINCRBY
     |                              |
     |                              v
     |                [WebSocket -> клиенты, тик 100 мс]
     |                              |
     |                              v  (по маркеру ROUND_END)
     |                   [Redis: история матчей]
```

### Ключевые решения

1. **Клики только через REST:** `POST /api/click`. Каждый клик получает явный ответ (`202`, `423`, `503`), ретрай с тем же UUID безопасен. WebSocket только для push (лидерборд, лобби).
2. **Kafka-консьюмер в том же приложении.** Отдельный воркер на 5-10 игроков не нужен.
3. **Одно глобальное лобби.** Новый игрок во время активного раунда получает `423 Locked`.
4. **Таймер раунда серверный.** Клиентский таймер только для UI.
5. **Топик `clicks` с одной партицией.** Порядок гарантирован, маркер конца раунда тривиален, 50 событий/с этого хватает с запасом.
6. **CQRS в явном виде не используется.** Запись (Kafka) и чтение (Redis ZSET) уже разделены инфраструктурно, дополнительная сегрегация на этой нагрузке оверинжиниринг. Обоснование в README.
7. **Virtual Threads, а не WebFlux:** нагрузка малая, клиенты Kafka/Redis/AMQP блокирующие, код проще и отлаживается обычными стектрейсами. Обоснование в README.

## 4. Функциональные требования

### 4.1. Лобби (Redis)

**Redis:**

- `HSET lobby:global:players {nickname -> joinedAt}`
- `HSET lobby:global:ready {nickname -> true/false}`
- `SET lobby:global:phase waiting|starting|running|finished`

**Рассылка событий:** RabbitMQ не используется. Любое изменение лобби (вход, готовность, старт) публикует внутреннее событие приложения (`ApplicationEventPublisher`). Обработчик **перечитывает состояние из Redis** и рассылает снимок всем сессиям `/ws/lobby`. Событие является только триггером, источник истины Redis. Это работает на одном инстансе; для нескольких понадобился бы Redis Pub/Sub.

**Логика:**

- `POST /api/lobby/join` выдаёт игроку `playerToken` (UUID, хранится в Redis и привязан к никнейму). Дубликат никнейма: `409`.
- Минимум 5 игроков: у всех появляется кнопка «ГОТОВ» (`POST /api/lobby/ready`).
- Проверка «все готовы» выполняется **атомарно** (Lua-скрипт или `WATCH`), чтобы два одновременных клика «ГОТОВ» не запустили два раунда.
- Все готовы: генерируется `roundId`, `phase = starting`, затем рассылается `game-start` с **абсолютным** `startAt = now + 3 с` и `roundEndTime = startAt + 60 с`. Клиенты стартуют по `startAt`, а не «по получении сообщения». Клиентам нужно синхронизировать часы по серверному времени из события.

### 4.2. Приём кликов (REST + Kafka Producer)

**`POST /api/click`**, заголовок `X-Player-Token`, тело `{ roundId, clickUUID }`.

1. Валидация: токен валиден, `roundId` совпадает с текущим, `phase = running`, `startAt <= now < roundEndTime`, `clickUUID` непустой UUID. Иначе `423` (раунд не идёт или закончен) или `400`.
2. Состояние раунда (`roundId`, `startAt`, `endAt`) кешируется **в памяти приложения**, без похода в Redis на каждый клик.
3. Сообщение `{ roundId, nickname, clickUUID, receivedAt }` (nickname берётся из токена, `receivedAt` ставит сервер) отправляется `kafkaTemplate.send("clicks", roundId, json).get(2, SECONDS)`. Блокирующий вызов в виртуальном потоке даёт естественный backpressure.
4. Таймаут или переполнение буфера продюсера: `503`. Успех: `202 Accepted`.

**Продюсер:** `acks=all`, `enable.idempotence=true`, `max.block.ms=5000`, `linger.ms=0..2`, ограниченный `buffer.memory`.

**Клиент:** шлёт клики параллельно, не дожидаясь ответа на предыдущий; хранит неподтверждённые и ретраит по таймауту с тем же `clickUUID`. Соединения keep-alive.

### 4.3. Kafka Consumer

**Конфигурация:** `AckMode.MANUAL`, `max.poll.records=50`, `enable.auto.commit=false`.

**Логика на каждое сообщение (строго синхронно в листенере):**

1. Если это клик и `receivedAt <= endAt` раунда, выполнить **один Lua-скрипт (`EVAL`)**: `SET dedup:{roundId}:{clickUUID} 1 NX EX 86400`, и только если ключ создан, `ZINCRBY leaderboard:{roundId} 1 {nickname}`. Два отдельных вызова запрещены (между ними возможна потеря или дубль, и расходуется лимит Upstash).
2. Только после успеха: `ack.acknowledge()`.
3. Redis недоступен: не коммитить, дать Kafka redeliver. После 3 ретраев: сообщение в DLQ-топик и коммит, чтобы не блокировать партицию.
4. Клики с `receivedAt > endAt` игнорируются (считаются «поздними»).

### 4.4. Конец раунда без потерь

В момент `endAt + 1 с` (запас на запросы, уже прошедшие валидацию) планировщик публикует в тот же топик маркер `ROUND_END{roundId}`. Поскольку партиция одна, когда консьюмер дошёл до маркера, **все клики раунда уже обработаны**. Только тогда он:

1. читает финальный `ZREVRANGE leaderboard:{roundId} 0 -1 WITHSCORES`;
2. записывает результат в историю матчей в Redis (п. 4.6);
3. ставит `phase = finished` и отправляет клиентам событие «раунд завершён».

Финальный экран берёт данные из `GET /api/round/{roundId}/results`. Читать итоги по таймеру без маркера запрещено: часть кликов ещё может быть в очереди.

### 4.5. Лидерборд и WebSocket

- Источник: `ZREVRANGE leaderboard:{roundId} 0 -1 WITHSCORES`.
- WebSocket `/ws/leaderboard`. Изменения аккумулируются, снимок отправляется **не чаще раза в 100 мс** (по одному обновлению на клик не слать).
- При 5-10 игроках проблем нет; при росте числа подписчиков рассмотреть WebFlux или лимит сессий (отметить в README).

### 4.6. История матчей (Redis)

История хранится в Upstash Redis (персистентный тир). Консьюмер пишет её **один раз**, при обработке маркера `ROUND_END`, атомарно (`MULTI/EXEC` или Lua):

- `HSET match:{roundId} finishedAt {время} winner {nickname} total {сумма кликов}`;
- ZSET `leaderboard:{roundId}` остаётся как есть и служит итоговой таблицей матча;
- `ZADD matches:history {finishedAtEpoch} {roundId}`: индекс матчей по времени.

Чтение: `GET /api/matches` (последние N через `ZREVRANGE matches:history`) и `GET /api/round/{roundId}/results` (`HGETALL match:{roundId}` + `ZREVRANGE leaderboard:{roundId} 0 -1 WITHSCORES`). Повторная обработка `ROUND_END` перезаписывает те же значения, поэтому запись идемпотентна. Ключи `dedup:*` живут 24 часа; `match:*`, `leaderboard:*` и `matches:history` без TTL (около 1 КБ на матч).

## 5. Graceful Shutdown и надёжность

**Настройки:** `server.shutdown=graceful`, `spring.lifecycle.timeout-per-shutdown-phase=30s`, `spring.kafka.listener.ack-mode=manual`, `producer.flush()` при остановке.

**Гарантия:** офсет коммитится **после** Lua-скрипта. Убили до коммита: Kafka отдаст запись новому инстансу, а дубль отсечёт dedup. Убили после: клик уже учтён.

**Инвариант для проверки:** число уникальных `clickUUID`, подтверждённых клиентом ответом `202` = `ZSCORE` игрока = число уникальных кликов в Kafka до маркера `ROUND_END`.

## 11. Приложение: контракт API

Этот раздел общий для бэкенда, фронтенда и ботов: все трое пишут код строго по нему. Формат данных везде JSON, время везде **epoch в миллисекундах (UTC)**, `roundId` и `clickUUID` это UUID в виде строки.

### 11.1. Общие правила

- Токен игрока `playerToken` выдаётся при входе в лобби. REST принимает его в заголовке `X-Player-Token`, WebSocket в параметре `?token=`.
- Любая ошибка (код 4xx или 5xx) возвращается в одном формате: `{ "error": "КОД", "message": "человекочитаемый текст" }`.
- Никнейм: 1-20 символов, буквы, цифры, пробел, `_` и `-`. Сравнение без учёта регистра.
- Минимум игроков для старта: 5 (значение `minPlayers` приходит в снимке лобби).

### 11.2. REST

| Метод и путь | Заголовок | Тело запроса | Успешный ответ | Ошибки |
| --- | --- | --- | --- | --- |
| `POST /api/lobby/join` | нет | `{ "nickname": "Vasya" }` | `200 { "playerToken": "uuid", "nickname": "Vasya" }` | `400 INVALID_REQUEST`, `409 NICKNAME_TAKEN`, `423 LOBBY_LOCKED` (идёт раунд) |
| `POST /api/lobby/ready` | `X-Player-Token` | `{ "ready": true }` | `200` (пустое тело) | `401 UNAUTHORIZED`, `409 NOT_ENOUGH_PLAYERS` (меньше 5), `423 LOBBY_LOCKED` |
| `GET /api/lobby` | нет | нет | `200` снимок лобби (см. 11.3, сообщение `lobby`) | нет |
| `POST /api/click` | `X-Player-Token` | `{ "roundId": "uuid", "clickUUID": "uuid" }` | `202` (пустое тело) | `400 INVALID_REQUEST`, `401 UNAUTHORIZED`, `423 ROUND_NOT_RUNNING`, `503 KAFKA_UNAVAILABLE` |
| `GET /api/round/{roundId}/results` | нет | нет | `200` результаты раунда (см. ниже) | `404 NOT_FOUND` (раунд неизвестен или ещё не завершён) |
| `GET /api/matches?limit=20` | нет | нет | `200` массив последних матчей (см. ниже) | нет |

**Правила для `POST /api/click`:**

- `423 ROUND_NOT_RUNNING` возвращается, если `roundId` не совпадает с текущим, раунд ещё не начался (`now < startAt`) или уже закончился (`now >= endAt`). Клиент после этого кода кликов не шлёт.
- `202` означает «клик принят Kafka» и возвращается **только после** подтверждения записи брокером. Дубликат `clickUUID` тоже получает `202`, потому что на уровне HTTP его не отличить, дедупликация происходит в консьюмере.
- На `503`, таймаут или обрыв сети клиент **повторяет запрос с тем же `clickUUID`** (с небольшой паузой). Другие коды 4xx не повторяются.
- Клиент не ждёт ответа перед следующим кликом: запросы идут параллельно, неподтверждённые хранятся в очереди для повторов.

**Ответ `GET /api/round/{roundId}/results`:**

```json
{
  "roundId": "uuid",
  "finishedAt": 1767225600000,
  "winner": "Vasya",
  "players": [
    { "rank": 1, "nickname": "Vasya", "score": 312 },
    { "rank": 2, "nickname": "Petya", "score": 298 }
  ]
}
```

**Ответ `GET /api/matches`:** `[ { "roundId": "uuid", "finishedAt": 1767225600000, "winner": "Vasya", "total": 1530 } ]`, новые матчи первыми.

### 11.3. WebSocket

Оба эндпоинта обычные WebSocket (не STOMP), сообщения текстовые JSON, направление только сервер → клиент. При подключении сервер сразу присылает текущий снимок.

**`/ws/lobby?token=...`**

| Сообщение | Когда приходит | Пример |
| --- | --- | --- |
| `lobby` | при подключении и при любом изменении лобби | `{ "type": "lobby", "phase": "waiting", "minPlayers": 5, "canReady": true, "players": [ { "nickname": "Vasya", "ready": false } ], "serverTime": 1767225600000 }` |
| `game-start` | когда все нажали «ГОТОВ» | `{ "type": "game-start", "roundId": "uuid", "startAt": 1767225603000, "endAt": 1767225663000, "serverTime": 1767225600000 }` |
| `round-finished` | когда консьюмер обработал `ROUND_END` и результат записан | `{ "type": "round-finished", "roundId": "uuid" }` |

Значение `phase`: `waiting`, `starting`, `running`, `finished`. `canReady` равно `true`, когда игроков не меньше `minPlayers`. Клиент стартует таймер и кнопку по `startAt`/`endAt`, пересчитав смещение часов как `serverTime - Date.now()`, а не «в момент получения сообщения».

**`/ws/leaderboard?token=...`**

| Сообщение | Когда приходит | Пример |
| --- | --- | --- |
| `leaderboard` | не чаще раза в 100 мс и только при изменениях | `{ "type": "leaderboard", "roundId": "uuid", "updatedAt": 1767225610000, "entries": [ { "nickname": "Vasya", "score": 42 } ] }` |
| `round-finished` | то же событие, что в лобби | `{ "type": "round-finished", "roundId": "uuid" }` |

После `round-finished` фронтенд запрашивает `GET /api/round/{roundId}/results` и показывает финальный экран. Итог из последнего сообщения `leaderboard` финальным считать нельзя: часть кликов может быть ещё в обработке.

### 11.4. Сообщения Kafka

Топик `clicks` (одна партиция), ключ сообщения `roundId`. Топик `clicks.dlq` получает те же сообщения, которые не удалось обработать за 3 попытки.

```json
{ "type": "click", "roundId": "uuid", "nickname": "Vasya", "clickUUID": "uuid", "receivedAt": 1767225610123 }
{ "type": "round-end", "roundId": "uuid" }
```

`receivedAt` ставит бэкенд в момент приёма. Консьюмер считает клик, только если `receivedAt <= endAt` раунда.

### 11.5. Ключи Redis

| Ключ | Тип | Что хранит | TTL |
| --- | --- | --- | --- |
| `lobby:global:players` | hash | `nickname -> joinedAt` | нет |
| `lobby:global:ready` | hash | `nickname -> true/false` | нет |
| `lobby:global:phase` | string | `waiting`, `starting`, `running`, `finished` | нет |
| `token:{playerToken}` | string | `nickname` | нет (чистится при выходе игрока и после раунда) |
| `dedup:{roundId}:{clickUUID}` | string | `1` | 24 часа |
| `leaderboard:{roundId}` | zset | `nickname -> score` | нет |
| `match:{roundId}` | hash | `finishedAt`, `winner`, `total` | нет |
| `matches:history` | zset | `roundId`, оценка = `finishedAt` | нет |
