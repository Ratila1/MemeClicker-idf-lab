# Техническое задание: платформа соревновательного кликинга в реальном времени

**Версия:** 1.1 (срок: 8 часов)

**Стек:** Java 25, Spring Boot 4.0.x, Spring MVC + Virtual Threads, **Gradle (Kotlin DSL, Wrapper)**, React + Vite, Kafka, RabbitMQ, Redis, PostgreSQL.

**Деплой:** Render.com (Web Service, Docker) + внешние managed-сервисы.

---

## 1. Цель

Мини-игра для соревновательного кликинга. Игроки заходят в единое лобби по никнейму. При наборе минимум 5 человек и единогласной готовности стартует 60-секундный раунд. Каждый клик проходит через Kafka, обрабатывается консьюмером и обновляет лидерборд в Redis. Фронтенд получает лидерборд и статус лобби по WebSocket. Итоги раунда сохраняются в PostgreSQL.

**Ключевые требования:**

- Игра стартует одновременно у всех (расхождение не более 1 с).
- 5 игроков × 10 кликов/с без деградации.
- Через 60 секунд кнопка блокируется, показывается финальный экран победителя.
- Идемпотентность кликов, backpressure, graceful shutdown без потери кликов.
- **Ни один принятый клик не теряется и не считается дважды.**

## 3. Архитектура

```
[React SPA] --REST--> [Spring MVC + Virtual Threads]
     ^                        |
     |<-----WebSocket---------+  (лидерборд, статус лобби)
     |                   +----+-----+
     |                   v          v
     |             [RabbitMQ]   [Kafka Producer]
     |              fanout      (клики, acks=all)
     |                   |          |
     |                   v          v
     |             [Redis]    [Kafka: clicks, 1 партиция]
     |             (лобби)          |
     |                              v
     |              [Kafka Consumer в том же приложении]
     |                              |
     |                  Lua: SET NX dedup + ZINCRBY
     |                              |
     |                              v
     |                [WebSocket -> клиенты, тик 100 мс]
     |                              |
     |                              v  (по маркеру ROUND_END)
     |                    [PostgreSQL: match_results]
```

### Ключевые решения

1. **Клики только через REST:** `POST /api/click`. Каждый клик получает явный ответ (`202`, `423`, `503`), ретрай с тем же UUID безопасен. WebSocket только для push (лидерборд, лобби).
2. **Kafka-консьюмер в том же приложении.** Отдельный воркер на 5-10 игроков не нужен.
3. **Одно глобальное лобби.** Новый игрок во время активного раунда получает `423 Locked`.
4. **Таймер раунда серверный.** Клиентский таймер только для UI.
5. **Топик `clicks` с одной партицией.** Порядок гарантирован, маркер конца раунда тривиален, 50 событий/с этого хватает с запасом.
6. **CQRS в явном виде не используется.** Запись (Kafka) и чтение (Redis ZSET) уже разделены инфраструктурно, дополнительная сегрегация на этой нагрузке оверинжиниринг. Обоснование в README.
7. **Virtual Threads, а не WebFlux:** нагрузка малая, клиенты Kafka/Redis/AMQP блокирующие, код проще и отлаживается обычными стектрейсами. Обоснование в README.

## 4. Функциональные требования

### 4.1. Лобби (RabbitMQ + Redis)

**Redis:**

- `HSET lobby:global:players {nickname -> joinedAt}`
- `HSET lobby:global:ready {nickname -> true/false}`
- `SET lobby:global:phase waiting|starting|running|finished`

**RabbitMQ:** fanout exchange `lobby-events`. Событие является **только триггером**: обработчик перечитывает состояние из Redis и рассылает снимок клиентам по `/ws/lobby`. RabbitMQ payload не источник истины.

**Логика:**

- `POST /api/lobby/join` выдаёт игроку `playerToken` (UUID, хранится в Redis и привязан к никнейму). Дубликат никнейма: `409`.
- Минимум 5 игроков: у всех появляется кнопка «ГОТОВ» (`POST /api/lobby/ready`).
- Проверка «все готовы» выполняется **атомарно** (Lua-скрипт или `WATCH`), чтобы два одновременных клика «ГОТОВ» не запустили два раунда.
- Все готовы: генерируется `roundId`, `phase = starting`, затем рассылается `game-start` с **абсолютным** `startAt = now + 3 с` и `roundEndTime = startAt + 60 с`. Клиенты стартуют по `startAt`, а не «по получении сообщения». Клиентам нужно синхронизировать часы по серверному времени из события.

### 4.2. Приём кликов (REST + Kafka Producer)

**`POST /api/click`**, заголовок `X-Player-Token`, тело `{ roundId, clickUUID }`.

1. Валидация: токен валиден, `roundId` совпадает с текущим, `phase = running`, `startAt <= now < roundEndTime`, `clickUUID` непустой UUID. Иначе `423` (раунд не идёт или закончен) или `400`.
2. Состояние раунда (`roundId`, `startAt`, `endAt`) кешируется **в памяти приложения**, без похода в Redis на каждый клик.
3. Сообщение `{ roundId, nickname, clickUUID, receivedAt }` (nickname берётся из токена, `receivedAt` ставит сервер) отправляется `kafkaTemplate.send("clicks", roundId, json).get(2, SECONDS)`. Блокирующий вызов в виртуальном потоке даёт естественный backpressure.
4. Таймаут или переполнение буфера продюсера: `503`. Успех: `202 Accepted`.

**Продюсер:** `acks=all`, `enable.idempotence=true`, `max.block.ms=5000`, `linger.ms=0..2`, ограниченный `buffer.memory`.

**Клиент:** шлёт клики параллельно, не дожидаясь ответа на предыдущий; хранит неподтверждённые и ретраит по таймауту с тем же `clickUUID`. Соединения keep-alive.

### 4.3. Kafka Consumer

**Конфигурация:** `AckMode.MANUAL`, `max.poll.records=50`, `enable.auto.commit=false`.

**Логика на каждое сообщение (строго синхронно в листенере):**

1. Если это клик и `receivedAt <= endAt` раунда, выполнить **один Lua-скрипт (`EVAL`)**: `SET dedup:{roundId}:{clickUUID} 1 NX EX 86400`, и только если ключ создан, `ZINCRBY leaderboard:{roundId} 1 {nickname}`. Два отдельных вызова запрещены (между ними возможна потеря или дубль, и расходуется лимит Upstash).
2. Только после успеха: `ack.acknowledge()`.
3. Redis недоступен: не коммитить, дать Kafka redeliver. После 3 ретраев: сообщение в DLQ-топик и коммит, чтобы не блокировать партицию.
4. Клики с `receivedAt > endAt` игнорируются (считаются «поздними»).

### 4.4. Конец раунда без потерь

В момент `endAt + 1 с` (запас на запросы, уже прошедшие валидацию) планировщик публикует в тот же топик маркер `ROUND_END{roundId}`. Поскольку партиция одна, когда консьюмер дошёл до маркера, **все клики раунда уже обработаны**. Только тогда он:

1. читает финальный `ZREVRANGE leaderboard:{roundId} 0 -1 WITHSCORES`;
2. записывает результат в PostgreSQL;
3. ставит `phase = finished` и отправляет клиентам событие «раунд завершён».

Финальный экран берёт данные из `GET /api/round/{roundId}/results`. Читать итоги по таймеру без маркера запрещено: часть кликов ещё может быть в очереди.

### 4.5. Лидерборд и WebSocket

- Источник: `ZREVRANGE leaderboard:{roundId} 0 -1 WITHSCORES`.
- WebSocket `/ws/leaderboard`. Изменения аккумулируются, снимок отправляется **не чаще раза в 100 мс** (по одному обновлению на клик не слать).
- При 5-10 игроках проблем нет; при росте числа подписчиков рассмотреть WebFlux или лимит сессий (отметить в README).

### 4.6. PostgreSQL

`match_results(round_id UUID, nickname VARCHAR, score INT, finished_at TIMESTAMP, winner BOOLEAN)`. Миграции через Flyway.

## 5. Graceful Shutdown и надёжность

**Настройки:** `server.shutdown=graceful`, `spring.lifecycle.timeout-per-shutdown-phase=30s`, `spring.kafka.listener.ack-mode=manual`, `producer.flush()` при остановке.

**Гарантия:** офсет коммитится **после** Lua-скрипта. Убили до коммита: Kafka отдаст запись новому инстансу, а дубль отсечёт dedup. Убили после: клик уже учтён.

**Инвариант для проверки:** число уникальных `clickUUID`, подтверждённых клиентом ответом `202` = `ZSCORE` игрока = число уникальных кликов в Kafka до маркера `ROUND_END`.

## 8. Критерии приёмки

- [ ] 5 пользователей заходят в лобби, нажимают «ГОТОВ», раунд стартует одновременно (расхождение не более 1 с).
- [ ] После истечения времени `POST /api/click` возвращает `423`; клиентский таймер не обходит серверную блокировку.
- [ ] При 5 ботах × 10 кликов/с система не падает, лидерборд обновляется с задержкой не более 500 мс.
- [ ] Дубликат `clickUUID` не увеличивает счётчик.
- [ ] Итоговые счета совпадают с числом уникальных подтверждённых (`202`) кликов: итог фиксируется только после маркера `ROUND_END`.
- [ ] При `kill -15` во время раунда после перезапуска ни один уникальный `clickUUID`, попавший в Kafka, не потерян.
- [ ] Новый игрок во время раунда получает `423 Locked`.
- [ ] Результат раунда сохранён в PostgreSQL и доступен по REST.
- [ ] `./gradlew build` и `./gradlew test` проходят из чистого клона.
- [ ] README содержит схему, расчёт бюджета Upstash, таблицу лимитов, обоснование Virtual Threads и отказа от CQRS.

## 9. Антипаттерны и запреты

1. **Запрещён** async-handoff в Kafka-листенере (`executor.submit()` + возврат из метода): офсет коммитится до обработки, при остановке клик теряется.
2. **Запрещено** генерировать `clickUUID` на бэкенде: только на фронте до отправки.
3. **Запрещено** использовать RabbitMQ payload как единственный источник истины. Только триггер «перечитай Redis».
4. **Запрещено** хранить `dedup:*` без TTL.
5. **Запрещено** раздельно вызывать `SET NX` и `ZINCRBY`: только одним Lua-скриптом.
6. **Запрещено** читать итоги раунда по таймеру без ожидания маркера `ROUND_END`.
7. **Запрещён** неограниченный буфер или очередь в памяти на пути кликов.
8. **Запрещено** полагаться на то, что Render не заснёт: прогреть сервис перед раундом, не деплоить во время раунда.
9. **Запрещён** CQRS в явном виде (в README абзац с обоснованием).
